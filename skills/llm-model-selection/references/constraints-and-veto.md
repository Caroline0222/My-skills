# 一票否决四闸 + 问客户 10 项

第 1 步与第 2 步。**这两步跑不完，不要进第 4 步比规格**——在已被排除的候选里比参数是白做，而且会被客户问出来。

---

## 第 1 步：四闸判定

许可 / 硬件显存 / 数据驻留 / 来源国别，**四条任一触发即排除，不做权衡**。

>硬约束不参与比选。这不是苛刻——拿一个数据出境都做不到的模型去比准确率，结论从第一步就站不住。

### 闸 1｜许可

**判断依据：读具体 checkpoint 的 LICENSE 文件，不是家族名。**

同一个家族不同 checkpoint，许可可能完全不同：

| 情况 | 判定 |
|---|---|
| Apache 2.0 / MIT，无收入门槛 | 通过 |
| Apache 2.0 + 附加使用限制（如超大规模商用另议） | 逐条读，触发则排除 |
| 自定义许可 + **收入门槛**（如集团年收入 > US$50M 需另签商业协议） | 客户收入超门槛 → 需商务确认，不算自动通过 |
| 明确禁止商用 / 限制行业 | 排除 |

**为什么必须读 checkpoint**：大厂旗舰模型的开源权重常改许可。同族新一代版本可能已从 Apache 2.0 改成带门槛的自定义许可。按"某某都是 Apache 2.0"来推断，会在评审时被法律或客户合规直接否掉。

**报告写法**：`Qwen3-32B-FP8 — Apache 2.0（modelscope.cn 模型卡，检索 2026-10）`，带上出处。禁止写"通义系列都是 Apache 2.0"。

### 闸 2｜硬件与显存

**判断依据：量化后 `权重 + KV cache ≤ 可用显存 × 0.85`。**

0.15 的余量留给推理框架、激活值、中间张量与碎片。压到0.9 以上会在压测时 OOM。

#### 权重显存换算（粗算够用）

| 精度 | bytes/param | 32B 模型约| 备注 |
|---|---|---|---|
| BF16 / FP16 | 2.0 | 65.5 GB | 精度基线 |
| FP8 | 1.0 | 34.3 GB | 需卡支持 |
| AWQ INT4 / GPTQ 4-bit | 0.5 | 19.3 GB | 单张 24GB 卡可跑，含量化元数据会略高 |

> 公式：`权重显存 ≈ 总参数 × bytes/param × (1 + 5% 量化开销)`。**MoE 的总参数决定权重显存**，不是激活参数。

#### KV cache 估算公式

```
KV_cache(单请求) = 2 × layers × kv_heads × head_dim × seq_len × bytes_per_element
```

- `2` = K 和 V 两份
- `bytes_per_element`：BF16 = 2，FP8 = 1
- GQA 会大幅压低 `kv_heads`（如 Qwen3-32B：64 个 Q 头但只有 8 个 KV 头，压到 1/8）

**算例（Qwen3-32B，32K 上下文，BF16）**：

```
2 × 64 层 × 8 kv_heads × 128 head_dim × 32768 seq × 2 bytes ≈ 8.6 GB / 请求
10 并发 → 约 86 GB KV cache
```

**这个算例要记住，因为它推翻了一个常见误解**：
> 4-bit 模型权重只占 19.3GB，看起来"单卡随便跑"。但在**长上下文 + 高并发**下，KV cache 可能比权重还大。19.3 + 86 = 105GB，**单张 24GB 卡根本放不下**。

所以闸 2 不能只算权重，必须算并发下的 KV cache。这是"参数看起来装得下、实际跑不起来"的典型原因。

#### 闸 2 常见误判

| 误判 | 纠正 |
|---|---|
| 用标称上下文算 KV cache | 用客户**真实文档长度 P95**，标称常是长尾极值 |
| 忽略框架与碎片，按 100% 卡算 | 留 15% 余量 |
| 用激活参数算 MoE 显存 | MoE 显存按**总参数**算 |
| 假设可切 CPU offload 无损 | 吞吐断崖式下降，要写进风险表 |
| 忽略多卡切分的通信开销 | 小batch 单机多卡优于张量并行（MoE 除外） |
| **套用 NVIDIA 的卡显存与量化格式** | 国产卡规格与算子支持不同，见下节 |

#### 非 NVIDIA 加速卡（信创 / 国产化场景必读）

**上面的算例全部基于 NVIDIA 生态。客户用国产卡时，下表每一项都要重新确认。**

| 项 | NVIDIA 侧 | 国产卡必须重新确认 |
|---|---|---|
| 卡显存 | 常见 24 / 48 / 80 GB | **各型号不同**，须查该卡型规格表，不能套用 |
| 权重/ KV cache 量化格式 | AWQ / GPTQ 生态成熟 | **支持的量化格式不同**，AWQ/GPTQ 未必可用 |
| 推理框架 | vLLM / SGLang 有官方 CUDA 后端 | 需确认该卡是否有可用后端、版本是否匹配 |
| 显存带宽与互联 | NVLink 生态 | 国产卡的互联方式不同，**大模型张量并行常受限于互联带宽** |
| 算子覆盖 | CUDA 算子齐全 | 某些算子缺失会导致模型无法加载或性能大幅下降 |

**闸 2 在国产卡场景的正确做法**（按顺序）：

1. **先查卡型规格表**，拿到该卡的**实际显存容量与带宽**——不要用"NVIDIA 24GB"的印象
2. **再查该卡支持的推理框架与后端版本**——框架不支持 = 方案不成立，这是比显存更早出局的原因
3. **再查该模型 checkpoint 在该卡上的可用性**——算子不全会加载失败或性能塌陷
4. 最后才用上面的公式算权重与 KV cache 装不装得下

> **顺序很重要：框架支持性比显存更早出局。** 一个 48GB 的卡如果框架后端不支持该模型，问题比一张 24GB 卡还严重。
>
> **报告里必须写明卡型全称**，不能写"AI 加速卡"或"国产卡"了事——客户技术负责人会追问具体型号与规格。

#### 客户已有硬件时的额外校验

客户已有卡型时，闸 2 要额外确认三件事：

| 项 | 问什么 |
|---|---|
| 卡型全称与规格 | 精确到型号，查该型号规格表 |
| 卡数与分配 | 推理卡几张、训练卡几张，能否挪用 |
| 卡间互联方式 | 决定张量并行是否可行，影响能跑的参数量上限 |

> **最后一条最容易被跳过。** 大模型多卡张量并行对互联带宽敏感，互联不足时"8 张卡"的实际能力远低于 8 张单卡的简单相加。**这一条直接决定选型档位**，不能只在报告里提一句。

### 闸 3｜数据驻留

**判断依据：推理、存储、备份三个位置都要在客户要求的法域内。**

只看推理节点在境内是不够的。三个位置逐个过：

| 位置 | 问什么 |
|---|---|
| 推理节点 | 物理位置在哪？云上则问可用区归属 |
| 存储 | 向量库、对象存储、日志落在哪？ |
| 备份 | 备份与快照存在哪？灾备副本呢？ |

**常见触发排除的情形**：
- 公有云 API（推理在厂商侧，客户无法验证驻留）
- 有跨境传输链路（即使数据加密，传输本身可能触发管制）
- 混合部署但备份落在境外

> 客户说"数据不能出境"时，要追问是**推理不能出**、**存储不能出**，还是**备份也不能出**。这三个的方案复杂度差一个量级。写进 C3/C4 两栏分别记。

### 闸 4｜来源国别

判断依据：客户国策 / 行业管制清单 / 出口管制要求。

- 政务、金融关键系统、部分国企场景有明确国产化或信创要求
- 香港场景不强制指定国别，但金融监管对数据可及时取回有要求
- 若客户有供应商白名单，此闸直接决定候选池

> **不确定客户是否有信创要求时，不要默认"没有"。** 按"有则国产优先"处理，并把这条列入附 A。

### 四闸汇总判定

| 闸 | 一句话判定 | 排除典型情形 |
|---|---|---|
| 1 许可 | 读具体 checkpoint 的 LICENSE | 非商用许可 / 超收入门槛 |
| 2 硬件显存 | 权重 + KV cache ≤ 可用显存 × 0.85 | 长上下文高并发下 KV cache 撑爆 |
| 3 数据驻留 | 推理+存储+备份三位置都在法域内 | 公有云 API / 备份在境外 |
| 4 来源国别 | 满足客户国策与管制清单 | 信创场景排除非国产 |

**四闸跑完，候选池应收敛到 2–3 个。** 收敛到 1 个 → 这是排除法，在报告里明说。收敛到 0 个 → 不要硬选，写"无可用候选 + 建议放宽哪条约束"。

## 第 2 步：问客户 10 项

| # | 约束项 | 判定口径 | 为什么模型清单替代不了 |
|---|---|---|---|
| C1 | 效果基线 | 准确率 / 通过率 / 人工评分口径 | **没有基线就没有目标，无法判断"够用"。** 客户说"要聪明一点"不是基线 |
| C2 | p95 时延 | 首 token 时延 + 完整响应时延 | 决定能不能用交互式架构、要不要流式 |
| C3 | 数据分级 | 内部 / 敏感 / 受管制 | 决定闸 3 的严格程度与是否要审计留痕 |
| C4 | 驻留法域 | 推理 / 存储 / 备份各自的位置要求 | 决定闸 3，且三处要求可能不同 |
| C5 | 输出语言 | 是否需生成粤语 / 繁中 | **能理解 ≠ 能生成**，见 `hk-context.md` |
| C6 | 许可类别 | 可商用 / 无收入门槛 / 需备案 | 决定闸 1，也决定后续能否转售 |
| C7 | 运维能力 | 有无 MLOps 团队 / 能否 7×24 | 决定是否推荐自建，否则运维成本被低估 |
| C8 | 年请求量 | 数值 + 增长预期 | 决定自建 vs API 的盈亏平衡点 |
| C9 | 峰值并发 | 数值 + 是否波峰集中 | 决定 KV cache 显存，直接影响闸 2 |
| C10 | 锁版要求 | 可换版 / 需长期锁版 | 监管场景常要求锁版 + 回归测试 |

### 追问话术（客户听不懂时怎么换说）

| 项 | 专业问法 | 客户听得懂的说法 |
|---|---|---|
| C1 效果基线 | 请给出准确率或人工评分口径 | "答错到什么程度你们能接受？100 条里错几条算不合格？" |
| C4 驻留法域 | 推理、存储、备份的部署位置要求 | "哪一步都不能出境？还是只有存数据不能出？" |
| C5 输出语言 | 是否需要生成粤语 | "客户是用繁体看，还是要AI 回广东话？" |
| C7 运维能力 | 是否有专门团队维护推理服务 | "上线后谁盯着？半夜模型挂了谁来重启？" |
| C8 年请求量 | 年度调用总量预估 | "一年大概被问多少次？" |
| C9 峰值并发 | 高峰时段同时在线调用数 | "开馆那半小时会有多少人同时问？" |
| C10 锁版要求 | 模型版本是否需长期固定 | "以后模型升级要不要重新报批？" |

### 常见口头答案的陷阱

| 客户说 | 陷阱 | 追问 |
|---|---|---|
| "数据不出境就行" | 没区分推理/存储/备份 | 三个位置分别确认 |
| "越快越好" | 无阈值，无法验收 | "多少秒以内算快？" |
| "要准确率高" | 无口径 | "谁来打分？多少分算通过？" |
| "开源的就行" | 未确认许可与运维能力 | 许可是否可商用？谁来维护？ |
| "用最便宜的" | 忽略了 R与 S | "重试算不算一次？失败的算不算成本？" |
| "先试点再决定" | 试点也要选型 | 试点阶段的约束与生产是否一致？ |

### 缺失时的行业默认值

**所有默认值标「假设，需客户确认」，并列入附 A。** 不要当成客户要求写。

| 约束项 | 政务 / 公共 | 金融 | 零售 / 文旅 | 制造 |
|---|---|---|---|---|
| C1 效果基线 | 准确率 ≥ 90% + 人工复核 | 准确率 ≥ 95%，关键动作双人复核 | 准确率 ≥ 85% | 准确率 ≥ 90% |
| C2 p95 时延 | 可放宽到 5s | < 2s | < 2s | < 3s |
| C3 数据分级 | 敏感 | 受管制 | 内部（含个人信息） | 内部 |
| C4 驻留法域 | 本地部署 | 境内 + 可及时取回 | 境内 | 厂区内|
| C5 输出语言 | 繁中/简中 | 繁中/英文 | **繁中 + 粤语** | 简中 |
| C6 许可类别 | 可商用 + 无收入门槛 | 可商用 + 可审计 | 可商用 | 可商用 |
| C7 运维能力 | 有专职团队 | 有 MLOps | 通常无 | 有工业IT |
| C10 锁版要求 | 需锁版 + 回归测试 | 需锁版 | 可换版 | 可换版 |

> 默认值只用来让选型往下走，**不用于给客户做承诺**。方案里出现默认值时必须标出来。
