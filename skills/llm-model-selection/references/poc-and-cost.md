# 跑 PoC + 算成本

第 5 步与第 6 步前半。这是选型里**最容易做假的一段**——PoC 可以做成"我想让谁赢谁就赢"，成本可以做成"比单价"。

---

## 第 5 步：跑 PoC

### 用例集规模

| 场景变化程度 | 用例数 | 说明 |
|---|---|---|
| 单一任务（如固定格式抽取） | ≥100 | 变化小，100 条能覆盖主要分布 |
| 多场景混合（客服 + 问答 + 摘要 + 生成） | 200–300 | 每个子场景至少 30 条 |
| 高度变化（长尾问答、开放生成） | ≥500 | 100 条会漏掉尾部case |

**抽样必须分层**，不能随便凑：

| 分层维度 | 分几层 |
|---|---|
| 任务类型 | 常规问答 / 边界情况 / 拒答 / 多轮追问 |
| 文档长度 | 短（<500token）/ 中 / 长（P95 以上） |
| 语言 | 简中 / 繁中 / 粤语 / 英文 |
| 难度 | 简单 / 常规 / 困难（需推理） |

**分层不是为了好看，是为了保证长尾不被平均掉。** 全部用简单题测，三个模型分数会挤在一起，看不出差异——然后就会有人拿0.5% 的差距说事。

### 20% 盲测集

- 从100 条里留 20 条不参与调试（prompt 迭代、规则修补都不许看这20 条的结果反馈）
- 盲测集结果由**业务方盲评**，不让技术团队自己判
- 理由：技术团队已经知道哪个是自己调的模型，有天然倾向

> 只有 20 条 → 盲评一致率的分母太小。**能扩到 50 条就扩到 50 条**，一致性才有意义。

### 业务方盲评仲裁

| 项 | 做法 |
|---|---|
| 评分人| 业务方 2–3 人，不含技术团队 |
| 评分方式 | 不知道模型身份（A/B/C 匿名），按统一 rubric 打分 |
| 分歧处理 | 分歧超阈值时第三人仲裁；仲裁后仍不一致的记为"待定" |
| rubric | 提前写死，**不许看完结果再改评分标准** |

**rubric 要可判**：

| 好rubric | 差 rubric |
|---|---|
| "答案中是否包含 [X][Y][Z] 三个要素，全含=2分，缺一=1分，缺二=0分" | "回答质量如何" |
| "是否违反 [某条业务规则]，违反=0分" | "是否专业" |
| "是否正确识别意图分类 A/B/C" | "理解是否准确" |

### 三维度打分（固定三样，不增不减）

| 维度 | 测什么 | 怎么测 |
|---|---|---|
| **质量** | 业务方盲评通过率 | rubric 打分 + 盲评一致性 |
| **单任务成本** | 每个成功任务的实际成本 | 实际 token 消耗 × 真实单价 ÷ 成功率 |
| **延迟** | p50 / p95 | 首 token 时延 + 完整响应时延，分开记 |

> **三个都要报。** 只报质量是常见的偷懒，但客户真正在意的是"够不够好+花多少钱+等多久"三件事。

### 同一套 prompt 跑所有候选

**硬规则**：所有候选用**同一版本 prompt**。禁止给某个候选单独调 prompt 再比。

理由：
- 调prompt 本身是工作量，给每个候选都调到最优，成本失控
- 一旦开始为A 调 prompt，A 的分数就不再是"模型能力"而是"这套 prompt + 模型"的合力
- 报告要交付给客户，必须能说"同一条件下比较"

**允许的调整**：
- 上下文截断策略可按各模型的原生窗口对齐（但要在报告里说明）
- 思考 / 非思考模式按各模型的最优配置跑（要注明每个候选跑的是哪种模式）

### 权重先定后跑

| 错误做法 | 正确做法 |
|---|---|
| 跑完看结果再定权重 | 跑之前就定好权重并写进方案 |
| 权重按"质量最重要所以给 80%" | 权重按客户业务价值定，且要问客户意见 |
| 看到某候选某维度差就调高该维度权重 | 不调，改成"该维度差异不显著，不参与排序" |

> **"跑完再定权重"是PoC 最常见的作弊方式。** 而且很容易被客户看出来——因为你会不自觉地让权重刚好倾斜到你已经偏好的那个候选。

### 「统计上接近」的判定

| 情况 | 判定 | 后续动作 |
|---|---|---|
| 差异 > 10% 且方向一致 | 显著 | 该维度可作为排序依据 |
| 差异 3–10% | 存疑 | 扩样或改 rubric 重跑 |
| 差异 < 3% | **不显著** | 写「无显著差异」，该维度不参与排序 |

**写进报告时**：
- 显著 → 写"A 优于 B 约 X%"
- 不显著 → 写「A 与 B 在此维度无显著差异」

> **绝不把 0.5% 写成优势。** 客户里有技术背景的人一眼看得出这是噪声，反而降低整份报告的可信度。

### 香港语料必须进 PoC

**没有公开横评可抄。** 通用中文榜单上的高分不代表繁中场景能用。

| 项 | 已知风险 |
|---|---|
| 繁中长题干 | 超过 600 token 后开源模型准确率明显下降 |
| 粤语 | 粤→普强于普→粤，**能理解 ≠ 能生成** |

**做法**：PoC 用例集里必须有客户真实繁中语料 + 粤语生成任务（若 C5 要求）。详见 `hk-context.md`。

## 第 6 步前半：算成本

### 计费口径三选一

| 口径 | 适用 | 关键变量 |
|---|---|---|
| **API 按 token** | 快速上线、量不大、无严格驻留要求 | 输入/输出单价、放大系数 R、成功率 S |
| **自建按 GPU 小时** | 数据不出境、高并发、需要锁版 | 卡数、小时成本、利用率、折旧年限 |
| **混合** | 大部分自建 + 长尾/峰值调API | 切分点与切换逻辑 |

> 混合是最常见的真实方案。**报告里要写清切分点**（什么条件下走自建、什么条件下调 API），这是客户运维最关心的部分。

### 公式 1：API 每成功任务成本

```
C_api = (T_in × P_in + T_out × P_out) × R / S
```

| 变量 | 含义 | 怎么取|
|---|---|---|
| `T_in` / `T_out` | 单任务输入 / 输出 token | PoC 实测均值（不是标称上限） |
| `P_in` / `P_out` | 输入 / 输出单价 | 厂商定价页，标检索日期 |
| `R` | 放大系数 | 含重试、工具调用往返、多轮。**实测，不是猜的** |
| `S` | 成功率 | PoC 实测。1 - 失败率 |

**放大系数 R 怎么估**：

| 场景 | R 参考 |
|---|---|
| 单轮问答，无工具调用 | 1.0–1.2 |
| 带 RAG 检索，一次命中 | 1.3–1.8（检索 + 重排 + 生成） |
| 多步工具调用 Agent | 2.0–4.0 |
| 多轮对话 | 累计长度 / 单轮长度 |

**成功率 S 怎么估**：用 PoC 实测。**写 100% 是不诚实的**——真实链路有格式错误、拒答、超时。

> **漏算 R 和 S 会系统性低估 API 成本。** 多步 Agent 场景下，两者能把估算拉高数倍。报告里 R 与 S 必填，漏填视为测算无效。

### 公式 2：自建每成功任务成本

**两种算法，按年请求量推算的是准的，按峰值并发推算会高估一两个数量级。**

```
✅ 年GPU 小时 = 年请求量 × 平均响应时长(秒) / 3600 × 单位换算系数 × 利用率
```
（`单位换算系数` = 每请求平均前向次数：单轮问答约 1，RAG 约 2–3，Agent 多轮按实际轮数）

```
⚠️ 峰值并发法（仅用于容量规划，不可用于算钱）：
   并发承载量 = 峰值并发 × 3600 / 平均响应时长(秒) × 单卡并发能力
```

| 变量 | 怎么取 |
|---|---|
| 利用率 | 保守 0.3–0.4，中性 0.5，乐观 0.65 |
| 单卡小时成本 | **待填 + 来源**（采购价÷折旧年限÷8760，或租用价） |
| 运维分摊 | 有 MLOps 团队则计真实人力；无则低估会更危险（见C7） |

```
C_self = (年GPU 小时 × 单卡小时成本 + 年运维分摊) / 年成功任务数
年运维分摊 = 人天 × 日成本 + 硬件折旧(3年)
```

> **为什么必须用年请求量法**：
> 峰值并发只发生在节假日的几小时，其余时间卡是闲的。按峰值并发年化，等于把一年都当成节假日在算——**实测差 25–50 倍**。
>
> 但峰值并发**必须**用来做另一件事：**验算卡够不够**。两个结论别混：
> - **算钱** → 年请求量法
> - **验容量** → 峰值并发法

> **利用率是最敏感的变量。** 0.3 与 0.65 之间差一倍以上。报告里必须标明用的是哪个假设，并做三档 TCO。

### 公式 3：GPU ↔ Token 等效换算

**这是自建 vs API 的唯一公平比较方式。**

```
等效单价 P_equiv = 自建年总成本 / 年 token 处理量
盈亏平衡请求量 Q* = 自建年固定成本 / (API 单价 − P_equiv)
```

| 判定 | 结论 |
|---|---|
| 客户年请求量 > Q* | 自建更省，且随量增长差距扩大 |
| 客户年请求量 < Q* | **API 更省**，尤其前期量小时|
| Q* 接近客户年请求量 | 混合方案，两套并行 |

> **不站队，用盈亏平衡点说话。** 客户问"自建还是 API"时，给 Q* 和客户的年请求量，让客户自己看结论。这比任何推荐都有说服力。
>
> 有个真实场景：客户已有硬件 → 自建的"固定成本"只剩运维，边际成本低，Q* 显著下降。有硬件和没硬件，结论可能完全相反。

### 口径陷阱

| 陷阱 | 后果 |
|---|---|
| 直接比每百万 token 单价 | **错**。不同模型 token 消耗差数倍 |
| 不计R | 低估 Agent / RAG 场景成本 |
| 不计 S | 低估，尤其是格式要求严的场景 |
| 只算 GPU 电费 | 漏了折旧、运维、机架、带宽 |
| 用峰值并发算年 GPU 小时 | 严重高估；真实利用率远低于峰值 |
| 用标称上下文算 token | 高估 |
| 忽略多模态的视觉 token 单价 | 视觉 token 常比文本贵数倍 |
| 三档 TCO 只填一档 | 客户看不出假设的影响 |

### 单价占位字段表

**本skill 不联网核实价格。** 所有单价留空由使用者填，并注明来源。

| 项 | 单价 | 单位 | 来源 | 检索日期 |
|---|---|---|---|---|
| 候选 A 输入 | 待填 | 元 / 百万token | 官网 / 客户报价 / 需确认 | |
| 候选 A 输出 | 待填 | 元 / 百万token | | |
| 候选 B 输入 | 待填 | | | |
| 候选 B 输出 | 待填 | | | |
| 自建单卡小时成本 | 待填 | 元 / 卡·小时 | 采购价÷折旧÷8760 / 租用价 | |

> **填了就要能指到来源。** 报价单一律脱敏，不写客户名与合同金额。
>
> **禁止凭印象填单价。** 厂商调价频繁且常有阶梯，写错会被客户当场发现。填不出来就留「需确认」。

### 三年 TCO 三档

| 档 | 假设 |
|---|---|
| **保守** | 利用率 0.3 · 请求量 +30%/年 · 单价不上浮 |
| **中性** | 利用率 0.5 · 请求量按客户预测 · 单价不变 |
| **乐观** | 利用率 0.65 · 请求量 +10%/年 · 单价下降 |

三档**都要填**。客户看三档的差异，才知道结论对哪个假设最敏感——这往往直接改变采购决策（早买还是先用 API 试）。

## 检查

进定结论之前逐项过：

- [ ] 用例集分层抽样，长尾未被平均掉
- [ ] 盲测集比例 ≥ 20%，且盲评由业务方做
- [ ] rubric 提前定死，未看完结果再改
- [ ] 所有候选用同一 prompt 版本（例外已注明）
- [ ] 权重跑之前定死，且已问客户意见
- [ ] 三维度（质量/成本/延迟）都有数据
- [ ] R 与 S 都是实测值，未猜测
- [ ] 成本按「每成功任务」算，未直接比单价
- [ ] 自建口径含折旧与运维，不只算电费
- [ ] Q* 已算出并与客户年请求量比对
- [ ] 三年 TCO 三档都填了
- [ ] 所有单价能指到来源，或已标「需确认」
- [ ] 不显著差异处写的是「无显著差异」
