# Anti-AI Style — 去 AI 味（售前方案语域）

## 核心原则

选型方案要像**顾问写给客户的项目组**，不像模型生成的报告。

判断标准很简单：**客户里的技术负责人读完，会不会觉得这方案是我们自己写的，还是工具生成的。**

售前方案的可信度建立在一件事上——**客户相信这个结论是我们判断出来的，不是套模板套出来的**。AI 味越重，信任度越低。

---

## 售前场景硬规则

| 规则 | 怎么做 |
|---|---|
| **每个结论挂依据** | 用约束编号（`[C3][C7]`）或来源（config.json /客户原文第X页） |
| **不吹效果** | 写PoC 实测值与用例集规模，不写"显著提升" |
| **不编价格** | 留占位标「待填 + 来源」 |
| **不只给一个答案** | 主推 + 备选 + 切换触发器 |
| **主动说局限** | 退步项、约束假设、需客户确认项都写 |
| **区分自己定的与协同的** | 方案层 / 研发层划界 |

### 最容易翻车的三处

| 位置 | 风险 | 纠正 |
|---|---|---|
| **给客户的一句话** | 客户唯一会记住的内容，写成口号就完了 | 必须含型号 + 硬约束依据 + 验证方式 |
| **核心理由** | 「综合评估后认为最优」= 没评估 | 每条理由挂约束编号 |
| **差异描述** | 把0.5% 说成优势，客户一眼看出 | 不显著就写「无显著差异」 |

## 高频问题词与替换

### 1. 互联网黑话 / PPT 词汇

| AI 味词 | 替换 |
|---|---|
| 赋能 | 帮 XX / 让 XX |
| 抓手 | 切入点 / 决定性约束 |
| 闭环 | 从 XX 到 YY 全流程打通 |
| 沉淀 | 整理 / 留下可复用方法 |
| 打造 | 做 / 搭|
| 体系化 | 按框架做 |
| 全链路 | 从入口到输出都覆盖 |
| 颗粒度 | 细到什么程度 |
| 底层逻辑 | 原理 / 依据 |
| 顶层设计 | 整体方案 |
| 深度融合 | 打通 / 集成 |
| 全面提升 | 写出具体维度与数字 |
| 高效智能 | 删除，写具体做了什么 |
| 精准匹配 | 匹配某条约束 |
| 强强联合 | A + B 组合 |
| 护城河 | 别人不容易复制的地方 |

> 客户技术负责人听到「赋能」「抓手」「深度融合」会立刻判断"这是 AI 写的"。

### 2. 形容词堆砌

| AI 味 | 替换 |
|---|---|
| 显著提升 | 写出数字与用例集规模 |
| 大幅优化 | 60% → 88%，通过率 |
| 卓越 / 领先 / 卓越 | 删除，写"排除了什么、选了什么" |
| 强大的推理能力 | 在 [某任务] 上盲评通过率 [X]% |
| 完善的生态 | 列出具体工具与版本 |
| 高可用 / 高并发 | 并发 [N]、p95 [X] 秒 |

**选型场景专用**：不用"性能优异""能力均衡""性价比高"。**改成对比**：比谁、快多少、省多少、贵多少。

### 3. 浮夸动词

| AI 味 | 替换 |
|---|---|
| 深入贯彻 | 按|
| 大力推进 | 推进 |
| 攻克 / 突破 | 解决 / 收敛 |
| 攻坚克难 | 解决问题 |
| 提质增效 | 提效率 |
| 深度赋能 | 直接说做什么 |

**选型场景专用**：不用"攻克选型难题"→写"候选池从 12 个收敛到 2 个"。

### 4. 时间描述

| AI 味 | 替换 |
|---|---|
| 在 XX 期间 | 2026.03 – 2026.06 |
| 近期 | 写具体月份 |
| 近年来 | 写年份范围 |
| 长期 | 写几个月 / 几年 |
| 持续 | 写做了多少次 / 多长周期 |

### 5. 抽象表述 → 具体行为

| AI 味 | 替换（举例） |
|---|---|
| 显著提升检索准确率 | 加 Reranker 后 top-3 命中率从 71% 到 86% |
| 有效降低推理成本 | 4-bit 量化后单卡可跑，GPU 需求从 4 卡降到 1 卡 |
| 提升模型响应速度 | 换 MoE 架构后 p50 从 1.8s 降到 0.9s |
| 优化资源利用率 | 利用率假设从 0.3 提到 0.5 |
| 增强系统稳定性 | 配第二个已批准模型并测过 failover |

## 售前语域专用替换

**这几组是售前场景高频、面试语境里不用的。**

| AI 味 | 替换 |
|---|---|
| 我方 / 甲方 / 乙方 | 我方 / 贵司 / 客户（按实际关系选） |
| 方案优势 | 这个方案在 [具体维度] 上更优，因为 [依据] |
| 完全满足需求 | 满足 C3、C7；C5 需PoC 实测 |
| 充分保障 | 兜底方案是 [X] |
| 有利于提升 | 能把 [指标] 从 [A] 提到 [B] |
| 具备强大的…能力 | 能做 [具体任务] |
| 丰富的实践经验 | 做过 [N] 个同档位项目（可举不涉密案例） |
| 强大的技术支持团队 | 有 MLOps 团队 / 由研发支持（按实际） |
| 方案灵活性高 | 可按 [X] 切换到备选 |

## 替换口径

### 数字优先

**任何模糊评价都能用数字 / 范围 / 频次替代。** 选型场景尤其严重——因为客户会核对 PoC 数据，报告里的形容词会和实测数据对不上。

| 写| 应该写 |
|---|---|
| 成本更低 | 每成功任务成本 [X] 元，比 [Y] 低 [Z]% |
| 效果更好 | 盲评通过率 [X]%，与 [Y] 无显著差异 / 高 [Z]% |
| 更快 | p95 [X] 秒 |
| 更省显存 | 4-bit 占 [X]GB，单卡可跑 |

### 主体具体化

| AI 味 | 替换 |
|---|---|
| 我们认为该选 X | 建议选 X，因为 [C3] |
| 该方案能满足… | 本方案满足 C1、C4；C6 需确认 |
| 系统能够自动… | 由 [组件名] 自动… |
| 方案设计了… | 块 3 定[架构]，块 6 算 [成本口径] |

**售前方案的主语是"我们 / 客户"，不是"我"。**（与面试语境相反——面试用"我"，方案用"我们 / 客户"。）

### 时间与版本具体化

- 所有时间段带具体年月
- 所有型号写 checkpoint 全名 + 版本日期
- 所有数据标检索日期
- 所有报价标生效期或"待确认"

## 自检流程

生成报告后逐块过：

1. **搜词扫描**
   - 搜 `赋能 / 抓手 / 闭环 / 沉淀 / 打造 / 体系化 / 全链路 / 颗粒度 / 底层逻辑 / 深度融合 / 护城河 / 强强联合`
   - 任一命中 → 替换

2. **依据检查**
   - 每个结论是否挂了约束编号或来源？
   - 核心理由有没有出现「综合评估」「充分考虑」这类空词？

3. **数字检查**
   - 每个优势是否都有数字？
   - 所有单价是否能指到来源，或已标「待确认」？
   - PoC 数据是否写了用例集规模与抽样方式？

4. **越界检查**
   - 有没有替研发定具体型号或量化位宽？
   - 方案层与研发层的边界是否清楚？

5. **脱敏检查**
   - 搜客户实名、报价金额
   - 命中即改行业代号

6. **朗读检查**
   - 把"给客户的一句话"念出声
   - 像不像顾问会**真的这么跟客户说**？
   - 不像 → 重写

---

## 兜底：让使用者复述自检

生成完报告后，**显式建议**：

> 请用你自己的话把"块 7c 给客户的一句话"重念一遍。如果你念的时候觉得哪里不像自己会说的，告诉我，我重写。

这个反馈循环比任何技术都管用。**顾问自己的话术，客户听得出来。**
