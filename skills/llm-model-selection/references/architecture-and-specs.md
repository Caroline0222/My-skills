# 定架构 + 比规格

第 3 步与第 4 步。**只处理已通过四闸的候选**，闸口没过的不进这两步。

---

## 第 3 步：定架构方向

### 交互形态 → 并发形态

| 交互形态 | 特征 | batch 区间 | 架构倾向 |
|---|---|---|---|
| 交互式问答（客服、助手） | 用户等回复，1人 1 请求 | batch ≈ 1–4 | **稠密赢**——单请求延迟最低 |
| 批量处理（离线抽取、标注、审核） | 吞吐优先，可排队 | batch > 32 | **MoE 赢**——激活参数小，吞吐高 |
| 混合（白天交互 + 夜间批处理） | 两种都有 | 分时 | MoE 或双部署，取决于波峰波谷比例 |

> **batch=1 稠密赢、batch>32 MoE 赢。** 这条判断比任何"MoE 更新更强"的印象都实用。

### 稠密 vs MoE 的真正区别

| 维度 | 稠密 | MoE |
|---|---|---|
| 显存（权重） | 总参数 × bytes | **总参数 × bytes**（不是激活参数！） |
| 单请求计算量 | 总参数 | 激活参数（通常 1/10 量级） |
| 单请求延迟 | 低 | 略高（路由开销） |
| 批量吞吐 | 线性增长 | **远好于稠密** |
| 显存优化空间 | 受总参数限制 | 同样受总参数限制，**MoE 不省显存** |

**最容易被讲错的一点**：
> **MoE 省算力，不省显存。** 显存由总参数决定。30B/3B 的 MoE 和30B 稠密占差不多的显存，但 30B/3B 解码快 2–3 倍、批量吞吐高得多。
>
> 客户问"MoE 是不是更省资源"时，答案要分两层说：**省算力，不省显存。** 只说前半句会被研发当场否掉。

### 多模态与 OCR

| 场景 | 额外成本项 | 备注 |
|---|---|---|
| 图文混排问答 | 视觉 token 消耗（远高于纯文本） | 视觉 token 单价常高于文本 |
| 版面还原、票据识别 | 需版面分析模型 / OCR 专用模型 | **不要用通用多模态顶替 OCR** |
| 图纸 / CAD 理解 | 视觉编码器与分辨率绑定 | 分辨率直接决定显存 |
| 视频 / 长文档 | 帧采样策略影响成本量级 | 采样率要写进方案 |

**判断依据**：客户的输入里**有多少比例是非文本**。占比 < 5% 时，多模态模型的额外显存与复杂度不划算，单独接 OCR 更省。

> 有项目在这一步做对了：通用问答应选纯文本模型，OCR 单独用专用模型，两者用同一套向量库索引。避免为了 5% 的图片把整个架构复杂化。

### 真实文档长度 P95

**不要用标称上下文。** 标称是长尾极值，真实业务文档通常短得多。

做法：从客户真实语料抽样 100–200 条，算长度 P95，再算 KV cache。

| 真实 P95 | 原生上下文够用? | 做法 |
|---|---|---|
| ≤ 8K | 大概率够 | 不需扩展，省 KV cache 显存 |
| 8K–32K | 看档位 | 用原生窗口优先 |
| > 32K | 需扩展或分块 | 扩展会牺牲精度，分块 + Reranker 更稳 |

**长上下文的隐性代价**：上下文越长，KV cache 显存线性增长（见 `constraints-and-veto.md`闸 2 算例），且长上下文里无关内容会拉低准确率。**能分块 + Reranker 就不要硬塞长上下文。**

### 消费级 / 边缘硬件陷阱

| 陷阱 | 说明 |
|---|---|
| 统一内存 ≠ 可用显存 | Mac 工作室机型的大内存部分被系统占用，且不可全部给推理框架 |
| 散热是硬上限 | 长上下文 + 多并发持续满载下，消费级芯片降频远快于服务器卡 |
| 无 NVLink | 多卡通信走 PCIe，MoE 的all-to-all 路由开销被放大 |
| 显存墙比算力墙更早到 | 4-bit 权重装得下，但 KV cache 装不下 |

> 真实场景里有客户指定用自有工作站（统一内存机型）跑本地模型。**结论通常是能做，但要降低并发预期并写进风险表**，而不是含糊说"可以跑"。

### 四维度法的定位（重要）

坊间常见的「任务复杂度 / 容错率 / 算力成本 / 部署方式」四维度打分法，是**有用的速记工具，但不是选型方法**。

| 四维度 | 在七步闭环里的正确位置 |
|---|---|
| 任务复杂度 | 第 3 步的输入（决定稠密/MoE、参数量档位） |
| 容错率 | 第 2 步的输入（决定是否必须人审、是否要更保守的档位） |
| 算力成本 | 第 6 步的输入（决定自建 vs API，但成本要算**每成功任务**） |
| 部署方式 | 第 1 步闸 3/4 的输出（**由合规倒推，不是自由选择**） |

**为什么不能当主干**：四维度不打分，就不知道该排除谁；不打分就可能把数据出境都做不到的模型拿进来比准确率。**顺序不能倒——先排除，再比选，最后才谈权衡。**

用四维度时，**放在第 3 步和第 6 步作为判断依据**，不要让它替代第 1、2 步。

### 输出：架构方向一句话

填进报告块 3。格式：
> "峰值并发 [N]、batch≈[X] → 采用[稠密/MoE]；输入中非文本占比 [X%] → [纯文本模型 + 独立 OCR]；真实文档 P95 [N] token → [原生窗口够用 / 需分块 + Reranker]"

## 第 4 步：比规格

### 候选池从哪来

**这一步之前必须先把候选列出来。** 没有候选池就无从比较，而候选池不能只有一个家族。

| 来源 | 怎么用 |
|---|---|
| **同档位主流开源权重** | 按参数量档位取 2–3 个家族的模型（如 30B 档取 A 家、B 家、C 家） |
| **同族不同架构** | 稠密 vs MoE 各取一个，用于验证架构判断 |
| **客户已指定/已在用** | 必须列入，即使不是最优——客户切换成本是约束 |
| **同档位闭源 API** | 若闸 3 允许，作为成本与质量的对照基线 |

**至少覆盖 2 个模型家族。** 只有一个家族时，客户会问"其他家看了吗"——这个问题在标书评审现场无法回答。

|候选池规模 | 判断 |
|---|---|
| 只有 1 个 | **不是选型**，写明"经四闸与档位收敛后仅 X 可行"，见 SKILL.md「什么时候根本不是选型」 |
| 2–3 个 | 正常比选范围 |
| > 4 个 | 收敛不足，闸口没跑完或档位定得太宽 |

**候选池为空或只有一个时的处理**：不要硬凑。写"在 [约束] 下，可行候选仅 [X]"并把放宽哪条约束的建议写进附 A。

### KV cache 必须自己算，不能只抄总显存

**块 4 的 KV cache 列需要三个字段，缺任何一个都算不出来。**

| 字段 | 从哪来 |
|---|---|
| `layers` | 官方 `config.json` 的 `num_hidden_layers` |
| `kv_heads` | `num_key_value_heads`（注意**不是** `num_attention_heads`） |
| `head_dim` | `hidden_size / num_attention_heads` |

```
KV_cache(单请求) = 2 × layers × kv_heads × head_dim × seq_len(P95) × bytes_per_element
```

> **只有 Qwen3-32B 一个模型在 `model-landscape.md` 里有完整字段，其余候选要自己回官方 `config.json` 查。** 查不到就在块 4 标「无法计算，需补spec」——**不要估一个数填进去**。
>
> 若客户的 P95 上下文短（如 ≤ 4K），KV cache 很小，可以在表里写"长上下文场景需重算"，不必逐个模型精算。

### 只在通过第 1、3 步的候选里比

闸口没过的不比；架构方向不同的分开比（稠密和 MoE 不放同一张表）。

### 横向对比 8 个维度

| # | 维度 | 为什么比这个 |
|---|---|---|
| 1 | 总参数 | 决定权重显存与许可范围 |
| 2 | 激活参数 | MoE 才看，决定计算量与吞吐 |
| 3 | 架构（稠密/MoE） | 决定延迟与吞吐特性 |
| 4 | 原生上下文 | 能否不用扩展方案 |
| 5 | 扩展方式与代价 | YaRN / NTK 等扩展会牺牲精度 |
| 6 | 4-bit 权重显存 | 决定单卡可行性（闸 2 已算，但这里要横向比） |
| 7 | KV cache @真实 P95 × 并发 | **决定实际能否跑** |
| 8 | 许可（checkpoint 级） | 闸 1 已过，但要在表里留痕 |

**补两列常见但容易漏的**：
- **多模态能力**：是否原生支持、视觉 token 成本
- **推理模式**：同一份权重能否切思考/非思考模式。差异极大（某 Qwen3 型号在 AIME 2025 上思考模式 72.9 vs 非思考 20.2）

### 显存档位换算表

| 精度 | bytes/param | 27B约 | 30B 约 | 32B 约 | 35B 约 |
|---|---|---|---|---|---|
| BF16 | 2.0 | 54 GB | 60 GB | 66 GB | 70 GB |
| FP8 | 1.0 | 27 GB | 30 GB | 33 GB | 35 GB |
| INT4 | 0.5 | 14 GB | 15 GB | 16 GB | 18 GB |

> 表内为裸权重估算，**实际需加5% 量化元数据 + 15% 框架余量**。报告中填数要注明是"裸权重估算"还是"实测占用"。

### 同一家族不同 checkpoint 许可可能不同

这是最容易翻车的地方：**不能按家族名推断许可。**

填表时每个候选的许可都要单独查该checkpoint 的模型卡。发现同族不同许可差异时，**要在报告里显式指出**（例："同族旗舰 checkpoint 已改自定义许可并设收入门槛，与本项目实际使用的中档 checkpoint 不同"）。

### 型号逐字核对规则

**型号的来源只有两个**：
1. 客户方案原文 / 招标文件 / 会议纪要
2. 官方 `config.json` / HF 模型卡 / 厂商文档

**禁止**：
- 推断型号（看到"30B 级"就写某个具体型号）
- 把家族名当型号（写"通义千问 Qwen"而不是具体 checkpoint）
- 凭记忆写参数量、层数、上下文

**为什么这么严**：同一项目里，PPT、技术方案、投标书三份文件可能写了三个不同档位的型号。**逐字核对客户原文，才不会在评审时被指出"你说的和我们标的不一致"。**

核对动作：
1. 打开客户方案原文，找到模型表述，**逐字抄**
2. 若客户只写品牌不写型号 → 标「由研发按客户算力定」，不推断
3. 若客户给了型号 → 抄完后用官方 config.json 验证参数，**不一致时以客户原文为准，并在报告里提示版本差异**

> 第三条容易忽略但很重要：客户方案里的型号可能已经过时。**不要擅自"升级"客户的型号**，而是照抄 + 单独提示"同档位已有更新版本，影响见块 4 备注"。

### 版本时效纪律

- 报告头必须标**模型规格检索日期**
- 说出旧型号时，**必须同步说同档位现有版本**
- `model-landscape.md` 超过 6 个月未重核 → 不许直接用其中的快照数据

>这条纪律的实际价值：模型迭代很快。方案里只写一个 2025 年的型号而不提同档位现状，会显得信息停在旧版本——**这在客户侧比"型号选错"更伤信任**。
