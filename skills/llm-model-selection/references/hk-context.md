# 香港与内地语境差异

ToB 方案里的地域语境。**这不是可选的加分项——香港场景搞错这几条，方案会直接不可用。**

---

## 繁中长题干性能拐点

**已知**：繁中题干超过约 600 token 后，开源模型准确率明显下降。

| 场景 | 风险 |
|---|---|
| 繁中单轮问答（短） | 影响不大 |
| 繁中长文档分析（>600 token 提问） | **开源模型准确率明显下降** |
| 繁中代码 / 表格 / 结构化输入 | 需实测，公开榜单不覆盖 |

**为什么发生**：多数开源模型训练语料中简中占比远高于繁中，长上下文中繁中的分布偏移被放大。

**方案里怎么写**：

| ❌ 错的写法 | ✅ 对的写法 |
|---|---|
| "该模型中文能力良好，可满足繁体中文场景" | "繁中短问答（<600 token）可用；长文档分析需在 PoC 中实测该场景准确率（块 5b 已列入繁中长文档分层）" |

> **方案里主动写出这个限制，比客户自己测出来强得多。** 而且它直接推导出 PoC 必须包含繁中长文档用例——这就是"能推导出动作"的知识，不是装饰。

## 粤语：能理解 ≠ 能生成

**已知**：粤→普强于普→粤。

| 方向 | 表现 |
|---|---|
| 粤语输入 → 普通话输出 | 相对好 |
| 普通话输入 → 粤语输出 | **明显弱** |

**所以要区分两类需求**：

| 需求 | 风险 | 方案 |
|---|---|---|
| **理解**粤语提问（转简中回答） | 低 | 通常可用，但要PoC 实测 |
| **生成**粤语回答 | **高** | 需实测；不达标则要人工模板或混合方案 |

> 港澳场景里"AI 要会说广东话"通常是真实需求。**这一条要单独立一个 PoC 分层，不能混在整体准确率里测。**

**若实测不达标，兜底选项**：
| 方案 | 代价 |
|---|---|
| 粤语用固定模板 + 槽位填充 | 灵活性低，但准确率可控 |
| 粤语生成交给闭源 API，自建只处理非粤语 | 架构变复杂，违反数据不出境时不可用 |
| 只做理解不做生成 | 需求降级，需客户确认可接受 |

## 香港政府与公共部门云取向

**关键**：**不是 Cloud First。**

| 项 | 内容 |
|---|---|
| 整体取向 | **私有云为主 + 混合云**，不是公有云优先 |
| GCIS 提供的服务 | IaaS / PaaS / DBaaS / CaaS 四类 |
| 立法会公开表述 | 「继续采用政府私有云」 |

**对选型的影响**：

| 倾向 | 说明 |
|---|---|
| 公有云 SaaS API 排除 | 数据驻留闸 3 通常无法通过 |
| 私有化部署是默认前提 | 不是"优先推荐"，而是"先排除公有云" |
| 混合云需要说明切分点 | 哪些走私有、哪些走公有，写清 |

> **这意味着对政府客户，"排除法"是主要形态。** 方案里应该先写"公有云 API 因驻留要求排除"，再做私有部署内部的比选——**顺序不能反**。

## 金融监管口径（香港）

**HKMA《Practice Guide on Cloud Adoption》**（2026-01-08 起适用）关键点：

| 项 | 内容 |
|---|---|
| 呈报要求 | 云项目占银行须呈报科技外判**约 80%**；**1/3–1/2** 涉及关键系统 |
| 地理辖区 | **不强制指定**，但要求数据能在港**及时取回** |
| 外判协议 | 最好受**香港法律管辖** |
| 取数通知 | 境外当局取数须**通知 HKMA** |
| 外判管理 | 参考《SPM SA-2》§2.9 |

**对选型的实际含义**：

| 常见误解 | 正确理解 |
|---|---|
| "HK 要求数据必须留香港" | **不强制指定地理辖区**，但要求可及时取回 |
| "所以可以随便用境外云" | 外判协议要受香港法律管辖、境外取数须可通知 |
| "数据加密了就合规" | 加密不改变驻留与取数要求 |

> **被追问"数据出境怎么答"时，准确口径是"不强制指定地理辖区，但要求可及时取回，且外判协议最好受香港法律管辖"。** 说成"必须留在香港"是编的，说成"随便出境"是危险的。

## 香港硬件现实

| 项 | 说明 |
|---|---|
| 消费级工作站路线 | 统一内存机型（如高端桌面工作站）可跑本地大模型，已有无 GPU 服务器的团队采用 |
| 优势 | 无需机房与运维、成本低、功耗可接受 |
| 限制 | **散热是硬上限**——长上下文 + 多并发持续满载下降频远快于服务器卡 |
| 无 NVLink | 多卡通信走 PCIe，MoE 的 all-to-all 路由开销被放大 |

**方案里怎么写**：
> "在客户自有工作站上可支持 [X] 并发 @ [Y] token。若峰值并发超过 [Z]，或需要长文档分析，建议评估增配第二台或采用混合架构。"

**不要含糊说"可以跑"**——要给并发数与文档长度的具体边界，并把边界外的情况写进风险表。

## 没有公开横评时的做法

**香港与粤语场景基本没有可信的公开横评。** 通用中文榜单不覆盖这些维度。

**唯一可信的做法**：用客户真实语料跑 PoC。

| 要求 | 说明 |
|---|---|
| 语料来源 | 客户真实业务数据，脱敏后使用 |
| 分层必含 | 繁中短 / 繁中长（>600 token）/ 粤语输入 / 粤语生成 |
| 盲测集 | ≥20%，业务方盲评 |
| 报告 | 标注这是客户场景实测，不是通用能力 |

**方案里的表述**：
> "公开评测未覆盖繁中长文档与粤语生成场景，因此本方案不引用公开榜单分数作为选型依据，改为以贵司真实语料 PoC 结果为准（块 5）。"

> **这一条是差异化点。** 大多数供应商会拿通用榜单说事，**明确说"我不拿榜单糊弄你，我们用你的数据测"**——这在客户侧很加分。

## 香港场景检查清单

- [ ] 繁中长文档（>600 token）用例已入 PoC
- [ ] 粤语生成单独作为一层测，不混在整体准确率
- [ ] 数据驻留的三个位置（推理/存储/备份）分别确认
- [ ] 政府客户场景已按"私有云为主"处理，公有云 API 已过闸 3 排除
- [ ] 金融客户口径准确：可及时取回 + 外判协议受香港法律管辖
- [ ] 若用消费级硬件，已给并发与文档长度的具体边界
- [ ] 方案中未引用公开榜单分数作为香港场景选型依据
- [ ] 语料使用已说明脱敏方式与客户授权范围
