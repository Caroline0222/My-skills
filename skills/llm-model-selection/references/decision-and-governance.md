# 定结论 + 上线治理

第 6 步后半与第 7 步。PoC 分数出来之后怎么选，以及上线后怎么管。

---

## 统计接近时按什么选

PoC 分数不显著时（任一维度差异 < 3%），**不要在质量维度上分胜负**。改按四个因子排序：

| 因子 | 判什么 | 怎么量化 |
|---|---|---|
| **成本** | 每成功任务成本 | 块6 的测算结果 |
| **时延** | p95 响应 | PoC 实测 |
| **治理** | 许可清晰度、数据可控性、供应商风险 | 定性 + 逐条列依据 |
| **集成复杂度** | 部署形态、改造成本、运维负担 | 卡数、改造工作量、是否需要新团队能力 |

**排序方式**：先看有没有**任一项存在硬差异**（如一个需私有化、一个不能）。有硬差异就直接定；没有再比成本，成本接近比时延，仍接近比治理与集成。

> **关键**：治理与集成复杂度是**定性判断**，报告里必须写成可核对的句子，不能只写"治理更优"。
>
> 好写法：「候选 A 权重 Apache 2.0 且无收入门槛；候选 B 为自定义许可且超门槛需商务确认」——客户能自己判断。
>
> 差写法：「候选 A 治理更规范」——客户无法核对。

## 不制造质量差异

| 分数情况 | 写法 |
|---|---|
| 差异 > 10% 且方向一致 | "A 优于 B 约 X%" |
| 差异 3–10% | "存疑，建议扩样重跑"，不参与排序 |
| 差异 < 3% | **「A 与 B 在此维度无显著差异」** |

**绝不把0.5% 写成优势。** 三个后果：

1. 有技术背景的客户一眼看得出是噪声，整份报告可信度下降
2. 一旦被指出，后续所有数字都会被重新审视
3. PoC 样本量通常不足以支撑小差异宣称，写了就是把噪声当结论

> **主动报告退步项反而更可信。** 例如某型号多语言指令跟随分数比上一代退步，但在竞技场榜单上超过某闭源模型。两边都说，客户才相信你的数据是真的。

## 主推 + 备选 + 切换触发器

**固定两行，缺一不可。**

| 角色 | 要求 |
|---|---|
| **主推** | 1 个。核心理由 ≤3 条，每条挂约束编号 |
| **备选** | 1 个。必须是**真实可切换**的方案，不是"次优"这种虚词 |

### 切换触发器要写成条件

| 差的写法 | 好的写法 |
|---|---|
| "视情况可切换到备选" | "若客户年请求量超过 Q*，或监管要求升级许可合规，则切换到 [X]" |
| "效果不达标时启用备选" | "若 PoC 质量维度盲评通过率 < 85%，或 p95 时延超过 [N] 秒，则切换到 [Y]" |

**切换触发器的作用**：让客户知道什么情况下方案要变。这是把"选型结论"变成"可持续方案"的关键一步，也是签完合同后不返工的前提。

> **只有一个模型 = 方案没有兜底。** 客户会问"模型挂了怎么办""供应商涨价怎么办""监管变了怎么办"——没有备选就只能现场回答，答不出专业度。

## 方案层 vs 研发层：结论怎么分层写

| 层 | 写什么 | 不写什么 |
|---|---|---|
| **方案层（售前）** | 许可可行性、部署形态、架构方向、性能档位、兜底方案 | 具体型号、量化位宽、引擎与并行策略 |
| **研发层** | 具体 checkpoint、量化精度、推理引擎配置、微调方案 | — |

客户原文只写品牌时：
> ✅ "锁定 [品牌] 系列，具体型号由研发按客户可用算力确定，建议 [稠密/MoE] 架构、4-bit 量化，具体 checkpoint 待研发确认后回填。"
>
> ❌ 直接写一个具体型号和参数。

**诚实划界比编一个型号可信得多。** 客户方技术负责人通常比售前更清楚该用什么引擎，划清边界反而显得专业。

## 上线治理三件套

**方案里必须写，不然后期出事没人兜。**

| # | 项 | 交付什么 |
|---|---|---|
| 1 | **回归测试集** | 从 PoC 用例集抽出固定子集（建议 50–100 条），每次变更后重跑 |
| 2 | **第二个已批准模型** | 上线前就把备选模型也走完审批流程（**不是出事了才申请**） |
| 3 | **测过 failover** | 实际演练一次切换，记录耗时与数据一致性 |

### 为什么第2 项最容易被忽略

> "备选模型"如果只是文档里的一行字，等真出事时要走采购、审批、安全评估，走完要几周——**那时候备选等于没有**。
>
> 正确做法：**上线前**就把备选模型纳入已批准清单，与主推同等审批。切换时只需运维操作，不需要重新走流程。

### 回归测试集的用途

| 触发场景 | 回归集做什么 |
|---|---|
| 模型换版 | 确认新版本没让效果退步 |
| 提示词改动 | 确认改动没破坏其他场景 |
| 检索数据更新 | 确认新数据没引入噪声 |
| 微调 / RAG 参数调整 | 确认调整是净收益 |
| 依赖升级 | 确认引擎升级没改行为 |

> 回归集不是 QA 的事，是**选型方案的一部分**。没有回归集的模型上线后就是黑盒，效果只能靠客户投诉才知道坏了。

## 重跑时机

**以下任一情况发生，选型结论必须重跑（不是重测，是重跑第1–7 步）：**

| 触发条件 | 为什么 |
|---|---|
| 供应商发布大版本 | 许可可能变、档位可能变优 |
| 客户业务量变化 > 50% | Q* 盈亏平衡点可能翻面 |
| 监管要求变化 | 驻留与许可闸口可能重开 |
| 检索数据或用户行为变化 | 第 3 步的 P95 长度、稠密/MoE 判断要重做 |
| 硬件换代或降级 | 闸 2 全部重算 |
| 同档位出现明显更优模型 | 候选池要重新收敛 |
| 距上次检索 **> 6 个月** | 模型快照过期（见 `model-landscape.md`） |

> **最常被忽略的是"业务量变化"和"同档位出现更优模型"。** 很多项目上线一年后还在用当初的选型，但从没回头看过是否还成立。

## 给客户的一句话说明怎么写

**≤60 字，含主推 + 核心理由 + 验证方式。** 这句话是客户唯一会记住的东西。

**结构**：`选 [型号]（[最关键的一条硬约束依据]），用 [客户真实语料 N 条] 跑 PoC 验证 [C1 目标]`

### 好例子

> "建议 Qwen3-32B（4-bit 单卡可跑，匹配并发 8 `[C9]`），已用 120 条真实工单跑 PoC，盲评通过率 88% `[C1]`。"

> "建议 [候选]（Apache 2.0 无收入门槛，满足港府采购要求 `[C6]`），PoC 质量与备选无显著差异，成本低 40%。"

### 差的写法

> ❌ "我们推荐业界领先的 XX 大模型，性能优越、性价比高。"——没有约束依据，没有验证数据
> ❌ "XX 模型是当前最优选择。"——"最优"不可核对
> ❌ "经过综合评估，我们认为 XX 模型能够满足贵司需求。"——综合评估 =没评估

**一句话里必须能看到约束编号对应。** 这是让客户相信"这个结论不是拍脑袋"的最短路径。

## 检查

交付前逐项过：

- [ ] 分数不显著处写的是「无显著差异」，没拔高
- [ ] 排序用了四因子，且治理与集成复杂度写成了可核对的句子
- [ ] 主推 + 备选各一行，备选是真实可切换的方案
- [ ] 切换触发器写成了条件，不是"视情况"
- [ ] 方案层与研发层边界清楚，没替研发定型号
- [ ] 回归测试集有数量与来源
- [ ] 第二个已批准模型的审批状态写明了
- [ ] failover 是否实测过写明了
- [ ] 重跑时机列了业务量变化与同档位新模型两条
- [ ] 给客户的一句话 ≤60 字且含约束编号与验证方式
- [ ] 报告头的模型规格检索日期在 6 个月内
